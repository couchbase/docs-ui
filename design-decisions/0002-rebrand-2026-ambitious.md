## Context
Phase A (palette tokens, logos) is done and the font swap was reverted because the team has no appetite for sitewide visual QE (see `design-decisions/0001`). The fonts have now arrived (`fonts/`: Inter, Centra No. 2, Open Sans), which unblocks the rest. This plan turns the grab-bag into staged work, revisiting each earlier item for more ambitious options. **QE cost is the main constraint**, so it is treated as a deliverable (Phase 0), not an afterthought. On approval, save as `design-decisions/0002-rebrand-2026-ambitious.md`.

## Decisions from Hakim (2026-10-21)
1. FontAwesome **Pro licence is available**. Centra web licence is **assumed OK for now: Hakim to double-check; do not block on it** (note this in the ADR and in the font CSS header comment).
2. **Links stay blue for now**, but make the link colour trivially swappable (single semantic token) so a later move to Red/Dark Red is a one-line change.
3. Syntax highlighting is pragmatic: readability for technical users first, brand colours as a "nod" where they fit; marketing will not review it. Green in dark-theme highlighting is fine.
4. Redocly is run manually per content repo (e.g. `docs-capella/redocly/theme.yaml`), so changes there are a **recommendation to copy manually**, not something this repo can ship.
5. Baseline design direction is **C "Quiet minimal"** (closest to today); A and B are alternates. Reviewer: Hakim, plus design-interested docs teammates; Web design joins at a defined checkpoint (see Phase 2).
6. **Upgrade the CSS tooling** (hardcoded/inlined variables have bitten before and block theming).
7. `preview-src` must be improved to represent important real pages (sample Redocly output, landing pages, each page type); team to propose candidates. Consider a fuller build pipeline (see Phase 0).

## Findings that shape the plan
- **Font files:** Centra No. 2 is **Medium only** (woff/woff2). Inter has Regular, SemiBold, Bold, Italic (no 300/500, no SemiBold Italic). Open Sans has the full set incl. woff2, so the site can **self-host** and drop the three render-blocking Google `@import`s in `site.css`. They are currently untracked in `fonts/` (plus `fonts.zip`; don't commit the zip). Gulp copies only `src/font/*.{ttf,woff,woff2}` (`gulp.d/tasks/build.js:102`), so they move to `src/font/`. No Centra licence file is included: confirm web licence covers docs.couchbase.com before shipping.
- **Build blocks theming:** production runs `postcss-custom-properties` with `preserve:false` (`build.js:51`), inlining every `var()`. Runtime dark mode is impossible until this changes. cssnano 4 / PostCSS 7 / autoprefixer 9 are too old for nesting, `color-mix()`, `light-dark()`, `@layer` (likely mangled). Options: upgrade to PostCSS 8 + cssnano 6 + `postcss-nesting`, or switch to lightningcss (nesting, minify, lowering in one step).
- **Contrast (computed):** links `#0074e0` pass on white (4.59) but fail on cream (4.09) and nav grey (4.36); hover/active link colours fail (2.2/3.6); every label fails at `opacity:.6` (1.6-3.1); admonition caution border 2.3; `#999` 2.85. **Correction to my earlier note: Couchbase Red `#EC1218` on white is 4.50 (passes AA, barely), not 4.3. On cream it is ~4.0 (fails).**
- **Syntax highlighting** is a hand-copied token-only theme (`highlight.css`, hljs 9.18.3, only 3 `--hljs-*` vars). Failures on the cream code background: `.hljs-built_in`/function titles orange `#fc9d0c` 1.88, regexp `#fd971f` 1.95, keyword/attr `#407787` 4.45 (just under). Comments are not dimmed.
- **Existing bugs to fix on the way:** `--color-muted` points at undefined `--color-brand-gray`; `nav.css:116` uses typo `--brand-color-gray1`; `--color-code` is defined but unused; `swagger-ui.css` styles a UI this repo doesn't ship; `intermediate-icon.svg` case mismatch in preview.
- **Redocly/REST API:** this repo only supplies the page shell (`body-rest-api.hbs`) and a `#redoc code` inherit rule. In content repos, `modules/<x>-api-reference/generate-docs.sh` runs `redocly build-docs --config theme.yaml` and **commits the output as a static HTML partial** (e.g. `docs-capella/modules/management-api-reference/partials/capella-management-openapi.html`) that a `:page-layout: rest-api` page includes via passthrough. So theme settings (fonts, `scrollYOffset: 114`, sidebar width) are **baked in at generation time** and need a regeneration + commit per module to change. There are 5 identical `theme.yaml` files (capella, capella-app-services, capella-copy, sync-gateway, enterprise-analytics; byte-identical md5, plus per-module copies), currently only setting Open Sans and sizes, no colours. `scrollYOffset: 114` is a hand-copy of the header height (`--height-to-body` = 7.1rem ~ 113.6px): any header-height change silently breaks Redoc anchor offsets.
- **Product-area hook already exists:** `navGroups` (site config JSON) can carry a per-group `color` (`search-catalog.js` already passes it); helper `nav-group-for-page` exists. `<body>` currently emits no component/group info (`layout-shell.hbs:8`), so adding `data-nav-group`/`--area-accent` there is the enabling change.
- **FontAwesome:** only free packages are installed; Pro (`fal`, `fa-sparkles`, etc.) is an `optionalDependency` needing a token, with a silent fallback ("FontAwesome Light icons not found"). `external-link-icon.css` uses a dead "Font Awesome Light" webfont path. Landing cards style `.svg-inline--fa` red 2em (`landing-page.css:327`).
- **Images:** best stipple candidates are `stars.svg` and `lineplus.svg` (capella landing pages), plus empty slots on `body-404.hbs` and home; per-product cards on landing pages. Unreferenced files to delete: `logo.svg`, `logo.png`, `couchbase-logo.png`, `menu.svg`, `video-media.svg`, `landing-icon.svg`, `social-icon/*`, two `landing-page-icon` files. Admonition/UI/logo icons stay flat.
- **Scroll hacks:** `main.css:6-30` injects a `::before` spacer on every `[id]` (+Firefox `@supports`), `03-fragment-jumper.js` rewrites DOM for Firefox, `06-page-rating.js` re-scrolls with jQuery (no offset), scroll-spy assumes the spacer. Native `scroll-padding-top` replaces all of it.

## Phase 0: Foundations (de-risks everything else)
1. **Representative fixtures + fuller build (the pipeline question).** Today `gulp preview` renders ~12 hand-written adocs against a fake `ui-model.yml` with `navMode: client`, a three-group sample nav and no real Antora output, so it can't show real nav depth, version selectors, nav groups, generated site-navigation data, search metadata, or a Redocly page (`rest-api.adoc` points at a spec but renders no Redoc). Proposed two-tier setup:

Copy and trim (e.g. `sdk.adoc` 1115 lines -> ~150; strip partial includes or bundle them) into `preview-src/`; record source repo/path/branch in a manifest so they can be refreshed.
   - **Tier 2 (new): a real Antora fixture build** (`npm run build:fixtures`) based on **`docs-site/antora-playbook.preview2.yml`** (chosen because it exercises recent UX concerns: preview banner with hidden link, watermark, AI Data Plane/Operational Insights renames, `override-url-component`, `site-generator-ms`, kroki/tabs extensions), generated by a small script rather than hand-copied so it stays in sync: take preview2 as-is, then (a) **reset the work-in-progress branch overrides to the main playbook's branches** (`docs-capella`, `docs-columnar`, `docs-ai` -> `main`; `docs-columnar-sdk-*` -> `release/1.0`; `docs-enterprise-analytics` drop `merge-prs/release/3.0`), keeping preview2's trimmed latest-version-only branches elsewhere for build speed (my reading of "reset to main"; if you meant every source should get main's full multi-version lists, that is a one-line option, at the cost of much longer builds), (b) point `ui.bundle.url` at the local `build/ui-bundle.zip` (pattern from `antora-playbook.preview.local.yml`), (c) override attributes needed for UI testing: `page-disable-chatbot: false` (preview2 disables the new Chat UI), keep `page-show-preview-banner`/`page-watermark`, (d) optional `--subset` allowlist (core ~12 sources: home, style guide, server, capella, capella-app-services, ai, one SDK, couchbase-lite, sync-gateway, operator, enterprise-analytics) for quick local runs; full 71-source run for CI/nightly. Requires GitHub access (some sources private) and the FA Pro token. Redocly coverage: the Capella management API partial is 6.1 MB and only exists on a WIP branch, so use a small committed partial instead (`docs-capella-app-services` `capella-openapi-metric.html`, 61 KB, on `main`; 600 KB-1 MB ones for a stress case), in current-theme and proposed-theme variants.
   - Open design choice: separate `docs-ui-fixtures` repo (clean, reusable by other teams, small maintenance burden) vs a `fixtures/` directory in docs-ui (simpler, bloats repo). Recommend a directory first; split out if it grows.
2. **Visual regression safety net:** Playwright screenshots of Tier 2 (and key Tier 1) pages at 3 widths, light now and dark later; baselines approved per PR. This replaces most manual QE and is what lets later phases land with confidence. Add axe-core and the contrast check to the same run.
3. **Tooling (approved):** upgrade PostCSS stack (PostCSS 8, cssnano 6+, autoprefixer 10, postcss-import 15+, postcss-nesting) or adopt lightningcss; set custom properties to be **preserved** in production; fix `npm install` / missing `algoliasearch/lite` so the build runs; update `browserslist`. Decide tool in a short spike (lightningcss is fewer moving parts; PostCSS keeps existing plugins such as `postcss-url`).
3. **Semantic token layer** in `vars.css`: `--surface-*`, `--text-*`, `--border-*`, `--accent-*`, `--link-*`, mapped from brand tokens (`--color-brand-black` is currently used for both backgrounds and text, which blocks theming). Convert ~25 stray hex values; fix the two variable bugs.
4. **Self-host fonts** into `src/font/` with `@font-face` (`font-display: swap`, preload Inter Regular + Centra Medium); keep Open Sans as the loaded fallback. Remove Google `@import`s.
5. **Bug/cleanup sweep:** delete unused images and dead CSS (swagger-ui.css if confirmed, FA Light path), commented code.

## Phase 1: Platform wins (a11y, scroll, CSS hygiene), low visual risk
- **Native anchor scrolling:** `html { scroll-padding-top: var(--h2-heading-top-space); scroll-behavior: smooth }` inside `prefers-reduced-motion: no-preference`; delete `main.css` spacer, Firefox JS, jQuery re-scroll (and likely jQuery itself if nothing else needs it); re-base scroll-spy offsets (IntersectionObserver).
- **Accessibility quick wins:** skip link + `id="main"`; global `:focus-visible` ring and remove the `outline:none` rules; `prefers-reduced-motion`; burger/nav toggles/version selector as real `<button>`s with `aria-expanded`; labelled `<nav>` landmarks (two header navs, doc nav as `<nav>`, TOC `aria-label`); `tabindex=0` on scrollable `pre`/table wrappers; copy button `aria-label` + live region; underline in-content links (not colour-only); print stylesheet gaps.
- **Larger a11y:** keyboard-operable nav tree (disclosure buttons or roving tabindex), 44px touch targets, verify tabs keyboard behaviour in `@asciidoctor/tabs`, table-responsive JS replaced by `td::before{content:attr(data-label)}`, heading-hierarchy audit on rendered pages.
- **CSS maintainability:** `@layer` (vendor, base, components, utilities) to remove most of the 57 `!important` (48 are margin utilities in `base.css`, generate them instead); native nesting + `:is()/:where()` for the long `.doc ...` chains and hover/focus pairs; `dvh` instead of `100vh` and the hard-coded `--height-footer: 310px` nav maths; `clamp()` fluid type to drop breakpoints; container queries for cards/tiles; `aspect-ratio`; `color-mix()` for hover/tint variants.

## Phase 2: Type and design direction ("modern" hypothesis)
- **Typography:** Centra No. 2 Medium for headings (h1-h3, landing hero, CTAs, search result titles), Inter for body/UI, Source Code Pro stays for code. Audit `font-weight` 300/500/600 usages: Centra has one weight and Inter lacks 300/500, so map heading weight to Centra Medium and body emphasis to Inter SemiBold; eyebrow/caption style per guide (Inter SemiBold 12px, +10% tracking). Inter is wider than Source Sans/Open Sans: re-check nav width, tables, TOC.
- **"Modern" is undefined, so test three hypotheses as switchable themes in the preview (`data-direction=...`) and review side by side.** **Baseline is C**, with A and B as alternates to borrow from: (C) *Quiet minimal*: near-flat, thin rules, restrained colour, content-first (closest to today, lowest QE risk); (A) *Warm editorial*: cream surfaces, big Centra headings, generous whitespace, 10-20px radii; (B) *Product console*: denser, white surfaces, cards with soft elevation, sticky contextual TOC, compact controls. Likely outcome is C plus selected A/B touches.
- **Review staging:** (1) Hakim iterates alone on tokens/type; (2) 2-3 design-interested docs teammates review the three-direction side-by-side once screenshots exist; (3) **Web design is invited at the decision gate** with a short brief (the three directions, what is fixed by the brand guide, what feedback is wanted: direction/feel, not pixel-level tweaks), and again at a pre-release review; time-boxed to avoid derailing. Elements to try across them: radius scale (5/10/20 via `--radius-*`), subtle Cream/Mid-Cream shading to distinguish content types (reference vs concept vs tutorial, admonitions, TOC/nav panels), sticky header shrink, better empty/404/search states.
- Decision gate: pick a direction before Phase 3 surface work.

## Phase 3: Colour and surfaces
- **Link colour: stay blue for now (decided).** Route all link colours through one semantic token set (`--link`, `--link-hover`, `--link-active`, `--link-on-dark`) so the later switch is one edit. Fix the failing hover/active blues now (2.2 / 3.6 on white) by deriving them from `--link` with `color-mix()` and checking contrast. If brand pressure arrives: Red `#EC1218` is 4.50 on white (passes barely) but ~4.0 on cream (fails), so prefer Dark Red `#7C0206` text with Red as accent, and gold on dark surfaces per the guide.
- **Search results:** result titles in Dark Red at smaller size for "gravitas" (verify contrast ~10:1 and hierarchy against snippet text); highlight/mark in Gold tint, not yellow.
- **Accent colours:** Gold for active/selected states and focus accents; Mid Cream/Sand for dividers and tags; Invalid Red `#FFD5D6` for form errors only; Highlight Green only for confirmations (copy success, "thanks" in helpful widget); Dark Teal illustration-only, so not for UI.
- **Labels:** drop `opacity:.6` and pick accessible solid colours (outlined pill style); same for admonition borders (caution 2.3).
- Footer to Cream, page background Cream vs White decided in Phase 2.

## Phase 4: Syntax highlighting rework
- Replace the hand-copied theme with a proper token palette built on the semantic layer, with light and dark variants, **all tokens >= 4.5:1** (validate in CI with a small contrast script over the token pairs). Fix orange tokens, `#407787`, dim comments, tint regexps/built-ins with palette-derived colours (Dark Red, Dark Teal-like, darker gold).
- **Green (approved, pragmatic):** use Highlight Green `#21EA2A` in the **dark** code theme (strings/diff-added on near-black); it fails as text on light backgrounds, so the light theme uses a darker green for the same role. No brand review needed; priority is readability for developers, with palette colours as a nod where they fit. Contrast script is the arbiter.
- Consider moving to highlight.js 11 (current is 9.18.3, with its old class names) or Shiki at build time if Antora pipeline allows; otherwise keep 9.x with a rewritten stylesheet. Also fix inline `a code` (4.09 on cream) and terminal/kbd/clipboard hard-coded colours.

## Phase 5: Dark mode
- `color-scheme: light dark`; tokens via `light-dark()` or `[data-theme]` overrides; follow `prefers-color-scheme` by default with a header toggle (Light/Dark/System) persisted in `localStorage` (try/catch), and a tiny inline `<head>` script to avoid a flash.
- Assets: logo swap via `<picture>`/two imgs (`couchbase-logo-white.svg` exists); admonition icons converted from baked-colour background SVGs to `mask-image` + `background-color: currentColor` or inline; nav chevron data-URI and `edit.svg`/`menu.svg` recoloured similarly; `social-icon/*` are unused (delete).
- Vendor: override instantsearch "satellite" theme variables in `docsearch.css`; chatbot is nearly all variables (easy); cookie banner not controlled here.
- **Redocly pages (recommendation only):** the shell themes with the site, but the Redoc body is static HTML with baked-in colours, so it **stays light** under dark mode unless regenerated. Deliverables in this repo: (a) a recommended shared `redocly/theme.yaml` (Inter/Centra fonts, brand palette for primary/links/http-verb colours, sidebar, right panel, code theme) with a short README listing the 5 repos/modules to copy it into and rerun `generate-docs.sh`; (b) in dark mode, give the Redoc container a light "card" frame with proper padding so it reads as an intentional panel, not a bug; (c) `scrollYOffset` kept in one documented place and matched to the header height (change = regenerate). A dark Redoc theme is an optional later step once (a) is rolled out; since the repos are not centralised, a script that copies the theme to all content repos would reduce manual effort.
- Dark screenshots added to the Phase 0 visual-regression suite.

## Phase 6: Product areas and FontAwesome
- Emit `data-nav-group` and `--area-accent` on `<body>` (`layout-shell.hbs`, using `nav-group-for-page` and the existing `navGroups[].color`); use it for a thin header/nav accent, active-nav marker, breadcrumb dot and an area icon next to the component title so readers can tell Server/Capella/SDK/Mobile at a glance. Palette needs agreed area colours (current sample model only defines Server red); keep contrast rules; stay on-brand (Red/Gold/Sand/Teal) with a couple of extras only if brand agrees.
- **FontAwesome (Pro licence confirmed):** keep Pro and make it first-class: document the token in README/CI so every build (including screenshot CI and contributors) gets Pro icons instead of silent free fallbacks (today `fal`/`fa-sparkles` quietly don't render without the token). Consider moving 5.13 to FA 6 Pro for a larger icon set and better brand/duotone options (check licence tier covers v6 and the `fontawesome-icon-defs.js` generator). Use duotone/light icons for product areas, FA Brands for product logos where available (custom SVG otherwise). Remove the dead `Font Awesome Light` webfont CSS (`external-link-icon.css`). All icons use `currentColor`, so they work in dark mode.

## Open consideration: merge docs-site and docs-ui? (raised 2026-10-21; not decided)

Prompted by lockstep pain (an Antora extension change plus a CSS/JS/template change needing two repos) and shared tooling (`populate-icon-defs` lives in docs-site but completes what docs-ui's committed `fontawesome-icon-defs.js` deliberately leaves out; the FontAwesome token lives in `docs-site/scripts/.npmrc`). Initial thoughts:

For:
- Atomic PRs for extension + template changes; one CI; no `prod-NNN` bundle-URL bumps in many playbooks to ship a UI change.
- The icon hand-off becomes one documented step in one place; one home for the FA token.
- Tier 2 fixture builds (and the visual suite on real content) stop being cross-repo choreography, and the Antora-version trap (stray `~/node_modules` Antora 3.1.14 vs docs-site's 3.2.0) disappears.

Against / to check first:
- **Visibility and licence:** docs-ui is MPL-2.0 and its releases are downloaded anonymously by playbooks; docs-site references private content sources and credentials tooling. Merging could force one side's visibility. This may be decisive; check with whoever owns the repos.
- **Other consumers** of the UI bundle (other sites, partner or preview playbooks) would still need a stable bundle artifact; `release.yml` already publishes one per branch push, which a merged repo would have to preserve.
- Different cadences and review audiences (UI changes are visible to everyone; playbook and extension changes are operational); history merge (subtree vs fresh); repo size (docs-site has 100+ playbooks, tests, content) and CI cost.

Alternatives that capture most of the benefit:
1. **Extract the `home/` component first** (as you suggested): it is already just another content source (`url: .`, `start_path: home`), so this is low-risk and decouples content edits from playbook/extension work regardless of the merge decision.
2. Keep two repos but make lockstep cheaper: docs-ui already publishes a release per branch push, so a docs-site branch can point `ui.bundle.url` at the matching docs-ui branch release (still two PRs, but testable together); move shared scripts (icon population) into one repo or a small package consumed by the other.
3. Monorepo with workspaces (`ui/`, `site/` with playbooks and extensions, `home/` extracted); decide after the fixtures build has shown how much the integration actually hurts.

Suggested order: extract `home/`; write down the contract between extensions and UI (data the UI expects: `navGroups`, site-navigation data, `page-*` attributes, icon defs, llms hooks); then revisit the merge with the visibility/licence answer in hand.

### Phase 2a: typography (2026-10-21, branch `rebrand-fonts`, stacked on `rebrand-phase0`)
Prioritised after Phase 0 because the Inter and Centra files were only declared there, so nothing used them.
- **Inter** is now the body/UI font (`--font-body`), replacing all 31 Open Sans / Source Sans Pro declarations. **Centra No. 2** (`--font-display`) is used for `.doc` headings, `.btn` and the Ask AI button, component-title and landing card titles, home headings. Chromium confirms Centra on h1/h2/buttons and Inter on body text and links.
- **Weights:** Inter ships only 400, 600, 700 and a 400 italic, so the 13 uses of weight 300 render at 400 and 500 renders at 400; no bold-italic exists (synthesised). Centra ships only Medium, so its `@font-face` declares `font-weight: 400 700` (every request uses the one file, never faux-bolded) and headings are set to 500. `h1` moved from light to medium; heading tracking from -0.025rem to 0 per the guide.
- **Preloads** for inter-400, inter-600 and centra-no2-500 in `head-last.hbs`; verified 200s and no preload warnings.
- **Observed effects:** headings are heavier than the old light/semibold Open Sans; nav and TOC items wrap more because Inter is wider than Source Sans Pro (the left nav and TOC used it); `h1` wraps to 3 lines on a 390px viewport where it used to take 2. No new horizontal overflow (checked against Phase 0). Accepted for now; sizes and nav width are design-direction questions for Phase 2 proper.
- **Kept on purpose:** Open Sans and Source Sans Pro stay declared (downloaded only if used) because the generated Redocly HTML names Open Sans in its baked-in theme. `redocly-theme.recommended.yaml` is the replacement to roll out per content repo (regenerate and commit each partial).
- **Tests:** `tests/visual/layout.spec.js` fails any page that scrolls horizontally. Four pages already did before this work (narrow widths: `server-concept-deep-toc` at tablet and mobile, `cbl-callouts` and `tiles` at mobile) and are marked expected failures.
